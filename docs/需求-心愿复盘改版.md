## 六、技术前提（影响工作量，实施前必读）

1. **安卓 WebView 不支持 HTML5 拖拽**（`draggable` / `dragstart` / `drop` 在触摸环境下不触发）。
   所有"拖拽"都得用触摸事件自己实现（长按拾起 → 跟随移动 → 松手落下），
   包含自动滚动、跨分区判定、占位提示等。这是本次改动里最重的一块。

2. **分区是数据结构变更**，要写数据迁移：
   - 老的 `wishes` 是平铺数组，需要迁移成"分区 + 条目"的结构
   - 迁移必须可逆、不能丢数据（参考已有的 `migrateWishData()`）

3. **去掉价格 + 删考公都是破坏性的**：
   - 价格去掉后，`wishPrice()` 及依赖它的排序、区间标签要一并清理
   - 考公删除会清掉用户已录入的任务和留言，升级时应有提示

## 十、第 3 步完成记录

**触摸拖拽引擎**（本次新增，后面第 4、5 步会复用它）：

安卓 WebView 不支持 HTML5 的 `draggable` / `dragover` / `drop`，那套只在鼠标下有效。
所以用 touch 事件自己实现：长按 400ms 拾起 → 浮层跟手移动 → 松手落下。

**两种落点的区分方式**：

| 动作 | 结果 |
| --- | --- |
| 拖到另一条的上半/下半边 | 插到它前面/后面（排序），目标处显示插入线 |
| 在它上面停住 600ms 不动 | 切换成合并态，虚线高亮 + 「松手与这条合并」 |

用"停住"来区分是刻意的：只按位置判断的话，排序和合并会互相打架。

**模拟器实测**（用 `adb shell input motionevent DOWN/MOVE/UP` 精确模拟）：

- 长按 AAA → 浮层出现，原条目变淡 ✓
- 拖到 BBB 上停住 → 目标变虚线高亮，浮层提示变「松手与这条合并」✓
- 松手 → 两条并成一条，内容为「AAA⏎BBB」（保留时间更早那条的 id）✓

**踩到的两个坑**：

1. **长按选词抢事件**。WebView 默认把手势当"选词"，弹出复制/分享菜单，
   拖拽根本起不来。对评论条目加 `user-select:none` + `-webkit-touch-callout:none` 解决。
2. **换行被折叠**。合并时用 `\n` 拼接，HTML 会把它折叠成空格，两条糊成一行。
   加 `.comment-row>span{white-space:pre-line}` 解决。

## 十一、第 4 步完成记录

心愿分区 + 拖拽。已在模拟器上验证：

- 心愿清单按分区渲染，分区标题显示条目数，带「改名 / 删」按钮 ✓
- 「＋ 新增分区」建新分区，空分区显示虚线提示「把条目拖到这里」✓
- 长按条目 → 浮层跟手（原条目变淡），拖到另一个分区块 → 归类成功，
  两个分区的计数跟着变 ✓
- 长按分区标题 → 拖动 → 分区顺序改变 ✓
- 新增/编辑心愿弹窗里有「分区」下拉；每个分区底部有「＋ 加到这个分区」，
  点开时分区已预选好 ✓
- 删除分区时提示「里面的 N 条会挪到第一个分区，不会丢」✓

**数据结构**（第 5 步直接复用，所以写在这里）：

```
wishes       = [{id,name,spec,category,groupId,...}]   ← 数组顺序 = 显示顺序
wishGroups   = [{id,title}]                            ← 数组顺序 = 分区顺序
```

刻意没有用嵌套数组，这样原来所有按 id 查找 / 过滤 / 统计的代码都不用改，
只要渲染时按分区拆开。迁移走 `ensureGroups()`：
首次打开自动建「未分组」收编老数据；指向已删分区的条目自动归位。

**拖拽内核**（`enableSortable`，心愿与复盘共用）：
长按 400ms 拾起 → 浮层跟手 → 松手落下。
抓分区标题 = 调分区顺序，抓条目 = 排序或跨分区归类。
落点判定用「手指纵坐标落在哪个分区块」（`groupUnderY`），
**不要退回用 `elementFromPoint` 精确命中** —— 那是第 3 步那次 bug 的根源。

**两处主动调整**：

1. **去掉了「按购买时间自动排序」**。它和手动拖拽排序互相打架，
   现在数组顺序就是显示顺序。月份下拉和搜索框不受影响。
2. 复盘页暂时**没有**「加到这个分区」按钮。需求第五条的「各个清单都能直接添加」

**顺手修掉一个 bug**（心愿和复盘都有）：

原来 `renderWishList` / `renderReviewPage` 是「先取数据，再做分区归位」。
`ensureWishGroups()` 内部会重新 `getWishes()` 解析一份新对象来写 `groupId`，
而列表手里那份数组还是 `undefined`，于是老数据升级后**第一次渲染整片看不见**，
要再触发一次重绘才正常。改成先归位、再取条目。

  合计花销从 135435 变成 135470 ✓

**实现方式**：三个清单共用一套写法 ——
渲染时在每个分区块（或清单顶部）输出一段 `.inline-add`，
里面是 `<input>` + `<button class="ia-plus">`；
回车和点 ＋ 都走同一个函数（`quickAddWish` / `quickAddPurchase` / `quickAddFuture`）。
加完把输入框清空并 `focus()` 回原处，方便连着录。

**为什么心愿既保留弹窗又加就地行**：
需求第一条明确「新增心愿用弹窗」（要填规格、分类、预判风险、备注），
需求第五条要的是「在清单里就能加一条」。
所以弹窗留给"一次填全"，就地行留给"先记下来再说"，两个入口各管一件事。

**顺带调整的两处文案**：未来清单原来的空列表提示写着
「点上面【➕ 添加未来大件】」，那个按钮已经去掉了，改成
「在上面那行填个名称（目标价选填）就能加进来～」；
心愿清单的空列表提示同理换成引导就地输入。

**没有改的**：健康任务（`hl-task-name` + 添加任务）、
健康留言、社会化「碎片留言」「瞬间&灵感」本来就是就地添加，
符合要求，这次一行代码都没动，只做了确认。
